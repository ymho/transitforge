# 正確な入力を要求しすぎる会話の改善（Issue #368）

## 監査範囲

前回の調査後に追加された非公開Feedback 5件を確認した。同じ相談に対する複数の評価を含み、
独立した5セッションとは数えない。地域まで示されていても、正確な場所や起点を要求する応答があった。
生会話、コメント、識別子は公開しない。実モデル評価は合成データのみを使う。

## 変更

- 事実を作らない原則を保ちつつ、「調査で確認する情報」「変更可能な仮定」「本人の選択」を分離する。正確な名称や駅を知らなくても手掛かりから調査する
- 当時の500文字制限に合わせ質問Toolの能力説明を短くし、地域からの調査・仮案・既知条件の維持・責務境界を含めた。後続変更で500文字切り詰め自体は廃止した（ADR 0044）。検索と、その結果で不要になる質問を同時に先回りして出さない
- `search_direct_routes.provisionalOriginStation`でモデルが地域の仮起点を提案できる。アプリは収録時刻表との一致だけを検証し、地域別の固定駅選択はしない。出発地が既知なら明示駅・Profileを優先する
- 出力の`TripJourneyPlan.originIsProvisional`と説明文で、現地起点の例であり自宅からの移動を含まないことを明示する。会話履歴・旅程保存・現在旅程のContext・経路再検索へ保持し、Profileやhard constraintへ昇格させない
- 未収録駅は実行前に拒否する。駅の実在確認は地理的な最適性や最寄りであることの証明ではない。地域との関係はAgentが情報源で調べ、経路と時刻は従来の決定論的検索を使う
- `planningStage=inspiration`または未作成・空のTripContextにProfileを要求していたmodel routingを、ADR 0048の候補発見phaseに合わせる。新model IDや常時二層の呼び出しは追加しない。Profile未登録の初回相談も既存decision classを使う

未確定の日付・泊数を勝手に確定すること、予約やProfileの自動書き換え、利用者の自宅位置の推測は
今回の対象外である。本人の出発地がなくても現地案は出せるが、戸口からの総所要時間は判断できない。

## 検証方法

決定論的テストは、時刻表にある駅と途中停車駅の照合、未収録駅の拒否、既知Profileの優先、
仮案の説明・保存・Contextへの維持を検証する。新しい発話routerや固定Plannerは追加しない。
Live Evalには地域のみ、施設名うろ覚え、仮の起点からの経路の3ケースを追加した。
外部検索結果はfixtureなので、実API込みの完遂率・自然な説明・地理的最適性を保証するものではない。

入力・Tool・Contextを揃えた3反復で採点し、未成功も保存する。質問の文章と`expectedInput`が
意味的に一致しているかは現在の自動採点では十分に検証できないため、Traceも確認する。
以前の天気・地域不一致の残課題は #365・#366で追跡した。以下は初期測定の記録であり、
後続修正と最新の完了判定は[旅行調査の統合検証](travel-research-integration-verification.md)を参照する。

## 初期検証結果（2026-09-09、後続修正前）

- `npm test`: Frontend 556件、Backend 128件、計684件成功
- `npm run build`、`npm run architecture:check`、`npm run workspace:check`成功
- 固定Observationの`eval:agent:smoke`は12/12、`eval:agent:full`は42/42成功
- 実モデル評価は20ケースを3反復した。新規の「地域だけの相談」「曖昧な施設名」「仮起点の経路」は各3/3成功。全体のstableは17/20、全ケース成功した反復は0/3であり、本番品質の全面合格とはしない
- 残る失敗は地域不一致2/3、天気の確認済み市区町村指定0/3、計画開始時の出発日確認0/3。最後のケースは確認済み地点の写真を再検索しており、不要な質問を減らす変更と必要な質問の維持を両立するうえで回帰の疑いがある。期待値を緩めず、Issue #368で追跡する
- 最終反復の合計は76 model calls、入力298,445 tokens、出力7,113 tokens、model latency合計54,281 ms。60タスク分の合計であり、一会話の遅延ではない。固定の追加model callは導入していないが、Profileなしの候補発見では既存decision modelを使うため、費用・遅延が不変とは主張しない

実モデルは`amazon.nova-lite-v1:0`と`jp.amazon.nova-2-lite-v1:0`を既存の構造化phase routingで使用した。
Grounded Claim Rate / Unsupported Claim RateはこのLive EvalではN/Aで、実世界の事実精度は測れていない。
ブラウザE2E、非公開会話の実モデル再送、デプロイ後の確認は未実施である。
専用format/lintコマンドは定義されていないため、型検査・build・`git diff --check`で確認した。
