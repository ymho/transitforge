# 旅程の保存済み天気

Trip正本の任意の`weather: TripItemWeather[]`に、各予定の予報観測を保存する。既存のV2/V3レコードはフィールドなしで読め、移行・自動補完は不要。料金と同様に取得時点の観測であり、現在の天気、運行可否、安全性の証明ではない。

## 保存と表示

各観測には予定ID、場所・日付・時刻から作るbasis、取得日時、1時間後の有効期限、Providerと出典、予報対象と予報行を保持する。時間が決まった観光はその現地時間の1時間予報、時刻未定・時間幅のある予定・宿泊は日別予報を使う。時刻未定から任意の時刻を作らない。

移動は経路全体の最初の出発地と出発時刻、最後の到着地と到着時刻だけを取得する。途中駅・乗換駅は対象外。鉄道は既存のstation-line-catalogから同名駅の座標が一意な場合だけ使い、曖昧・未収録・取得失敗なら未取得とする。駅名を市名に読み替えない。日付またぎでも出発・到着それぞれの現地日時を使う。

座標が保存済みならOpen-Meteoに直接渡す。その他の場所は保存済みの地域名または場所名で既存の市区町村検索を使い、検索できなければ未取得とする。保存した実際の予報地点名が予定の場所名と異なる場合は画面に併記する。

予報は現地の今日から15日後まで。複数日の宿泊・柔軟な日程は取得可能な期間だけを保存し、日別タイムラインは表示中の日の予報を選ぶ。時間別予報は該当する現地の時間帯だけを保持し、日別予報から時間別予報を捏造しない。Providerのraw応答は保存しない。

予定の展開領域に天気・気温・降水確率と取得日時、Open-Meteoの出典をコンパクトに表示する。未取得の天気を晴れや降水0%として表示しない。期限を過ぎても保存観測として表示し、「更新できます」を付ける。予報期間外・取得失敗は別の状態として表示する。

## 更新API

認証済みTrip APIの`refresh-weather`は`tripId/itemId/baseRevision/mutationId`を受ける。予定と対象はServer正本から導出し、Browser/AIの申告した予報値は保存しない。予定カードの「天気を更新」からだけ実行し、初回表示、画面再読み込み、通常のTrip get/list、AIのTrip参照は外部天気を再取得しない。

同じbasisの取得済み観測が1時間以内なら再利用する。取得失敗は再試行できる。保存は既存のCASとmutation receiptを使い、競合時に古い日時・場所の予報で上書きしない。予定自体、確定状態、費用は変えない。予定の場所・日時・カレンダーbinding変更や削除では古いbasisの観測を除去する。名称変更や他の予定の編集では一致する観測を維持する。

OwnerとEditorだけ更新でき、Viewerは保存済み予報を読める。共同編集の保存には既存Participant/Grantのtransaction fenceを使う。公式しおりは日付のないモデル旅程なので予報を公開・複製しない。公開create要求からProvider観測を持ち込むことはできない。

Trip API Lambdaは既存のViewer用`viewer-input/train_index.json`だけをS3 GetObjectで読める。外部通信は各要求3秒、鉄道カタログはSDKの1回・3秒に制限し、最大2地点を並行取得する。追加のAPIキー、Bedrock呼び出し、定期ジョブは不要。

## AI参照

通常のTrip Context、対象予定のuiFocus、`get_trip_items`のprojectionにも保存済み観測と`weatherSemantics`を渡す。取得日時とvalidUntilを保持し、保存済み予報を最新の実況と扱わない。既に場所・日時のbasisが変わった観測はContextへ出さない。

## 確認

Domainで対象範囲・変更時の除去・公式しおりへの非公開、Applicationで保存・再読込・CAS・idempotency・共有権限、Adapterで座標照会、UIで表示・明示更新・Viewerの読取専用、AI projectionで同じ観測の参照を検証する。テストは合成予報と既存の鉄道fixtureを使い、外部Providerやモデルは呼ばない。

予報の`retrievedAt`はProvider応答の受信時刻まで許容する。処理開始後に取得された正常な観測を未来時刻として除外しない。受信時刻より未来の観測は除外し、キャッシュの観測日時・有効期限はそのまま保持する。

## Trip天候候補と局所変更

Tripの観光・飲食候補検索は、同じ認証済みTripに保存された起点の地域と日付が揃うとき、共通の天気予報Providerへその日付を問い合わせる。未定の日程や地域では照会しない。Tripのrevisionは検索結果に添え、検索・候補比較はTripを更新しない。

予報は`forecast`、判定は`weatherContext`として返す。Providerの予報日、取得時刻、有効期限、freshness、WMO codeが有効なときだけ雨の比較材料とする。予報期間外、日付不一致、期限切れ、取得失敗は`unconfirmed`または`unavailable`で区別し、晴天や季節傾向へ置き換えない。将来の季節傾向が必要なら別の根拠を取得する。観光・飲食Providerの結果は天気の部分失敗でも残す。両ProviderのEvidenceを一つのTool結果から別々に投影する。

雨の強い予報では座標を持つ候補だけ、Tripの保存済み起点との**直線距離**で近い順のIDを別途返す。検索Providerの元順位と全候補は保持する。座標がない候補の距離は不明のままとし、屋内性、実経路、滞在時間、営業時間を推測しない。主目的地や確認済み予定を検索時に削除・移動しない。

旅行中やTrip確定後の調整は既存の`propose_trip_item_change`とTrip画面の確認・CAS経路を使う。利用者が変更対象を指定してから個別項目の変更案を作り、予約や購入の状態を自動で変更しない。古い天気結果や変更前の日付は新しいTrip revisionへ持ち越さず、変更後は新しい日付・地域を再照会する。
Tripのactivityには「天気を踏まえて相談」から対象項目をfocusして相談へ戻る導線を置く。この操作ではTripも予約も変更せず、以後の変更案は既存のbefore/after、影響表示、確認操作で採用する。

この段階の検証は合成Providerの天気、期間外、古い予報、取得失敗、候補とTrip不変を対象とする。実Provider・画面の予報期間外/取得失敗/雨予報E2Eは#758で行う。
