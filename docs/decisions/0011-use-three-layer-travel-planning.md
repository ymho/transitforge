# ADR 0011: 旅行計画を3レイヤに分離し、直通列車を自前データで確定する

- ステータス: Accepted
- 日付: 2026-08-14

## コンテキスト

外部経路APIだけで旅行案を確定すると、TransitForgeが保持するJR西日本の計画ダイヤ、
4時境界の業務日付、列車別遅延と食い違う可能性がある。一方、宿泊・観光・天気・地図を
すべて自前で収集することは目的ではない。初期段階で乗換探索まで含めると、正しさの検証
範囲も急激に広がる。

## 決定

旅行計画を次の3レイヤに分ける。

1. `transitforge-data-builder` はJR時刻表の収集、raw保存、正規化、当日を含む31日間の
   ローリング保持、日次補完、直通検索インデックス生成を担当する。
2. TransitForgeは時刻表、列車、遅延データを正として直通区間を再評価し、比較可能な
   旅行候補を組み立てる。
3. Mapbox、Rakuten Travel、OpenWeatherなどは宿、観光、地図、天気の補助に限定する。

Bedrockには既存の`search_direct_routes`をツールとして公開する。ツール実行はブラウザで
始まるが、経路探索は保護されたAI Lambdaの`journey_search`操作で
行う。出発駅を省略した場合の最寄り駅選択だけは端末内で行い、座標はバックエンドへ送らない。

日本の鉄道経路を個人利用可能な外部APIへ依存できないため、data-builderは列車の隣接停車駅を
時刻付き接続へ正規化した`timetable-connection-index-v1`を生成する。TransitForgeは接続を
時刻順に走査し、同一列車の継続、最低乗換時間、乗換上限、列車番号別遅延を評価する。
初期のBedrockツールは`maxTransfers=0`で直通に限定し、探索器は後続フェーズ向けに乗換を扱える。
各検索は制約別の除外件数と採用経路を`journey-search-trace-v1`として構造化ログへ残す。

MVPはJR西日本内で同一列車に乗り続けられる区間だけを対象とする。乗換探索、予約、宿泊、
観光、天気の統合は直通検索の精度を確認した後に追加する。外部APIの秘密情報はブラウザへ
置かず、呼び出しはサーバー側の境界に置く。

## データ契約

`direct-service-index-v1`は営業日ごとに次を持つ。

- `service_date`、`timetable_kind`
- 出発可能駅から`service_uid`への`station_origins`索引
- `service_uid`をキーとする列車情報と、順序付きの停車駅、着発時刻（営業日内の分）

最終候補の出典は常に`transitforge`とし、外部候補の参照IDは発見経路を監査するためだけに
保持する。

## 影響

- 外部経路APIの提供範囲や契約条件に検索可否を左右されない。
- rawから正規化結果を再生成でき、日単位の欠損を検出・補完できる。
- 直通のみという制約がドメイン境界で明示され、乗換対応を別フェーズにできる。
- 日次処理は当日分を再生成し、さらにローリング期間の最古の不足日を既定1日補完する。
  初回構築時は`--fill-limit 30`を指定する。
