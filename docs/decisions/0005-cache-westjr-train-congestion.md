# 0005: JR西日本の列車混雑情報を低頻度キャッシュ経由で参照する

## Status

Accepted（Bedrockへ返す分析範囲はADR 0007で一部置換）

## Context

列車番号に対応する車両別混雑情報を、列車上の棒グラフとして表示したい。
`https://www.train-guide.westjr.co.jp/api/v3/trainmonitorinfo.json` は、
列車番号をキーとして編成・車両ごとの `congestion` を返す。

このURLはブラウザ向けのCORS許可ヘッダーを返さず、公開された安定API仕様も
リポジトリには存在しない。また、表示の滑らかさのために短周期でアクセスする
必要はなく、大量アクセスを避けなければならない。

## Decision

- ブラウザは上流URLへ直接アクセスせず、同一オリジンの
  `/api/westjr/trainmonitorinfo.json` を参照する。
- ローカル開発ではViteミドルウェアが上流レスポンスを5分間メモリキャッシュする。
- 同時リクエストは1つにまとめ、複数タブや再読み込みによる上流アクセスを抑える。
- クライアントの更新間隔は1分とし、非表示タブでは更新しない。
- 利用者が混雑表示をオフにしている間も更新しない。
- 取得失敗後は15分待ってから再試行する。
- `congestion` が0以上の車両だけを合算し、列車番号単位の棒グラフへ変換する。
- 棒の高さには上限を設けず、混雑合計1あたり0.1mの線形スケールで表示する。
- 取得失敗や形式変更時は棒グラフを表示せず、列車表示そのものは継続する。
- 本番環境を追加する場合も、同等以上の共有キャッシュを持つ同一オリジンの
  プロキシを用意する。ブラウザから上流へ直接ポーリングしない。
- AWS開発環境ではEventBridge SchedulerからLambdaを1分間隔で1回だけ起動し、
  上流レスポンスを共有キャッシュへ保存する。Schedulerの再試行は無効化する。
- 重複起動時の上流アクセスを防ぐため、取得前に分単位のS3キーを
  `If-None-Match: *` で条件付き作成する。最初に取得権を得た実行だけが上流へアクセスし、
  取得権オブジェクトは2日後に削除する。
- 最新レスポンスはWeb用S3の `/api/westjr/trainmonitorinfo.json` へ上書きし、
  CloudFrontから最大60秒キャッシュで配信する。
- 取得時点ごとの生レスポンスはgzip圧縮し、JSTの年月日・時刻で分割した
  非公開S3アーカイブへ保存する。既定の保持期間は730日とする。
- 毎分取得時に、棒グラフと同じ車両別`congestion`合算ロジックで、全列車合計、
  列車数、車両数、列車番号別合計を算出する。
- 分析用サマリーはDynamoDBへ1スナップショット1項目で保存し、JST日付を
  パーティションキー、収集時刻をソートキーとする。TTLはS3と同じ保持期間にする。
- S3の生レスポンスを正本、DynamoDBを再生成可能な検索索引とする。
- AI駅員の日別ピーク検索はDynamoDBだけを読み、Bedrockへはピーク観測と
  上位5列車だけを返す。1日分の生JSONをモデルへ送らない。

## Consequences

- ローカル開発サーバー単位の上流アクセスは、正常時に最大でも5分に1回となる。
- AWS開発環境の上流アクセスは正常時に1分に1回となり、ブラウザ数には比例しない。
- 現在の混雑情報とローカル時刻表の列車番号が一致した列車だけに棒が表示される。
- 上流レスポンス形式が変わると混雑表示は停止するため、パーサーのテストと
  失敗時の安全なフォールバックを維持する必要がある。
- Viteのメモリキャッシュはプロセス再起動で失われる。
- S3には1日1,440個、1年で約52.6万個の小さなアーカイブオブジェクトが作成される。
  Athena等で長期分析する際は、小さいファイルを日次・時間単位でまとめる処理を
  後続で検討する。
- DynamoDBには1日最大1,440項目をオンデマンド課金で書き込む。列車単位の書き込みには
  分割せず、上流アクセス回数も増やさない。
