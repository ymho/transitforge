# ドキュメンテーション方針

現行仕様を読む場所と、判断の履歴を分ける。一つの主題に一つの正本を置き、通常の変更はその文書を更新する。コード・validator・テスト・Terraformが実行契約を所有し、文書は意味、制約、責務、操作・運用手順を説明する。

## 配置と読む順番

[文書索引](README.md)から、プロダクト概要、全体構成、対象機能の仕様、必要な運用手順へ進む。

| 配置 | 役割 |
| --- | --- |
| `product-brief.md` | 利用者価値・対象範囲 |
| `architecture/` | 全体構成、責務、認証、保存・通信・外部境界 |
| `specs/` | 現行の機能仕様。独立した変更理由・所有境界を持つ主題ごとに分ける |
| `operations/` | 実行可能な検証・デプロイ・復旧手順 |
| `data/` | 生成入力・出力データ仕様 |
| `decisions/` | ADR。重要な判断の背景・代替案・影響。現在の手順書ではない |

READMEは入口と開発コマンド、各サービスのREADMEはその実行環境に限定する。仕様本文を複製せず、正本へリンクする。プレビュー・検証手順は運用文書へ集約する。

## 更新と削除

- 挙動・契約・設計・コマンドを変えた変更では、同じPRで既存の正本文書を更新する。
- 新規文書は既存主題へ統合できない場合だけ追加する。Issue番号、日付、PR単位で仕様を分割しない。
- 仕様には最終状態を書く。「今回」「後続」「実装開始時」「完了報告」はIssue・PRへ置く。未公開の能力は内部契約と公開操作を明確に分け、公開済みと誤認させない。
- フィールド一覧、コード全文、テスト結果・件数を転記しない。重要な意味・制約を書き、実装と隣接テストへ案内する。
- 廃止時は後継へ有効な制約を移し、リンク・文書チェック・索引を更新して旧文書を削除する。空の転送文書や一括archiveは作らない。履歴はGitとIssue・PRから確認する。
- 完了した移行、監査、個別試験結果は原則削除する。再利用する測定手順・基準は運用文書へ、判断理由はADRへ残す。
- ADRは重要な選択に限る。UIの細かな調整・実装完了報告では追加しない。番号を再利用せず、置換時は状態と後継を明示する。過去本文は当時の記録として保持する。

## 登録と検証

現行のdocs内文書は`catalog.json`へ登録し、索引にリンクする。ADR本文はADR索引で管理する。docs外の現行READMEも同じcatalogへ登録する。履歴節を現行仕様に同居させない。

`npm run docs:check`は登録漏れ、索引漏れ、相対リンク、参照ファイル、npm script、実装のないpreview、既知の廃止契約、ADR索引を確認する。新旧の意味の整合は人がコード・テストと照合する。自動チェック成功だけで仕様の正しさを保証しない。
